## 1. Current-State Architecture Assessment

### What Shipped (R1 through R3b-3)

HarkenIQ is code-complete across all four layers with 1663 tests:

| Layer | Service | Status | Key Capabilities |
|---|---|---|---|
| L1 Node | Agent (`src/harkeniq/`) | 83 Python files | Redfish polling, 5 skill types, 7 actions, trending, heartbeat mesh, quorum, claims, suspicion, partition fencing, playbooks, credential rotation |
| L2 SM | Site Manager (`services/site_manager/`) | 34 Python files | gRPC ingest, correlation (4 rules), incidents, approvals, LLM Explain, skill generation/validation/distribution, knowledge base |
| L3 CC | Central Command (`services/central_command/`) | 28 Python files | Fleet poller, approval routing, outcome aggregation, pattern detection, knowledge distribution, learning feedback (R-C1 complete) |
| L4 Console | Harken Console (`services/console/` + `console-ui/`) | 39 + 47 files | Keycloak OIDC, RBAC (7 roles), Ed25519 licensing, billing (Razorpay+Stripe), support ticketing, 22 React screens |

### Validated Gaps

The following gaps are grounded in concrete operational scenarios, not generic DevOps checklists.

#### Gap 1: No integrated deployment exists

**Scenario:** Operator installs HarkenIQ at a 50-server site.

**What breaks:** There is no single Docker Compose that starts Agent + SM + CC + Console + databases + Keycloak. The deploy/ directory has separate Compose files for SM and R2b, but no full-stack composition. An operator cannot validate end-to-end behavior.

**Evidence:** `deploy/site_manager/docker-compose.yml` (44 lines), `deploy/r2b/docker-compose.yml` (72 lines). No unified Compose.

#### Gap 2: Database migration chain incomplete

**Scenario:** Operator upgrades HarkenIQ from v1 to v2 on an existing deployment.

**What breaks:** CC and Console have Alembic `env.py` but empty `versions/` directories. The SM has `0001_initial.py`. Schema evolution on a running database is impossible for CC and Console.

**Evidence:** `services/central_command/src/harkeniq_cc/db/migrations/versions/` is empty. `services/console/src/harkeniq_console/db/migrations/versions/` is empty.

#### Gap 3: No observability

**Scenario:** Production incident -- agent stops reporting. Operator needs to determine: is the agent down, is the SM unreachable, or is the gRPC connection timing out?

**What breaks:** No structured logging (Python logging to stdout only). No distributed tracing (no request IDs flow across Agent -> SM -> CC). No metrics (no Prometheus endpoint). Debugging requires reading raw log lines across three services.

#### Gap 4: Protocol coupling blocks device extensibility

**Scenario:** Customer has 50 servers (Redfish) and 20 switches (Arista, gNMI). HarkenIQ can only monitor the servers.

**What breaks:** Agent's Poller imports `RedfishClient` directly. Skills engine operates on protocol-agnostic `NormalizedDevice`, but no `DeviceProtocol` abstraction exists to plug in alternative transports.

**Evidence:** `src/harkeniq/poller.py` lines 48-58 branch on vendor (Dell/HPE) and call vendor-specific normalizers. `src/harkeniq/agent.py` line 141 instantiates `RedfishClient` directly.

**What's already protocol-agnostic:** Skills engine (0% Redfish references), trending, diagnosis, autonomy, actions model, claim protocol, quorum. These operate on `NormalizedDevice` dataclasses.

**What's Redfish-coupled:** ~850 LOC (37%): `redfish/client.py`, `redfish/discovery.py`, `redfish/dell.py`, `redfish/hpe.py`, parts of `poller.py` and `actions/executor.py`.

#### Gap 5: No air-gapped LLM capability

**Scenario:** Government/defense customer deploys HarkenIQ in an air-gapped network. LLM Explain and skill generation require cloud API access.

**What breaks:** `LLMProvider` at SM uses httpx to call OpenAI/Anthropic cloud APIs. `NullLLMProvider` gracefully degrades (deterministic reasoning still works), but the AI-visible product value vanishes.

### Safety Implications

| Capability | Safety Risk | Mitigation |
|---|---|---|
| Config compliance auto-remediation | Auto-changing config could break services | Dry-run mode first; require SM approval for write actions |
| Firmware update orchestration | Bricked device = permanent loss | Never update >1 device per fault domain simultaneously; require human approval for batch |
| Network device monitoring | Switch misconfiguration = network outage | Read-only monitoring by default; write actions require T1 quorum + SM + CC approval |
| Air-gapped LLM | Smaller model = worse reasoning | NullLLMProvider fallback always available; LLM is advisory, never decisional |

## 3. Proposed Release Boundaries

Based on the dependency graph, codebase analysis, and operational prerequisites, R4 decomposes into four subslices:

### R4-0: Platform Validation and Operational Foundation

**Objective:** Prove that R1-R3b operates as one integrated system. Every item here unblocks a concrete HarkenIQ deployment scenario.

**Scope:**

| Item | Operational Scenario It Unblocks |
|---|---|
| Full-stack Docker Compose (Agent + SM + CC + Console + TimescaleDB + Keycloak) | "Install HarkenIQ" -- operator can deploy in one command |
| Alembic migration chain for CC + Console (backfill from models.py) | "Upgrade HarkenIQ" -- schema evolves without data loss |
| End-to-end smoke test (agent registers, polls, detects fault, proposes action, CC approves, agent executes, outcome recorded) | "Validate the deployment works" -- proves all four layers integrate |
| Structured logging (JSON, with request-id propagation across Agent->SM->CC) | "Debug a production issue" -- trace a request across services |
| Health check endpoints (probe DB, downstream gRPC, cache) | "Monitor HarkenIQ itself" -- operator's Nagios/Datadog can poll us |
| Prometheus metrics export (gRPC latency, queue depth, error rates, agent count) | "See HarkenIQ performance" -- Grafana dashboard for ops team |
| Secrets management (env vars + Docker secrets; Vault optional in R4-1+) | "Secure the deployment" -- no hardcoded passwords in compose files |
| Graceful shutdown (drain pending RPCs on SIGTERM) | "Restart without data loss" -- stretch goal, not exit-gate blocking |
| `DeviceProtocol` abstraction (interface only, refactor Redfish into it) | "Extend to non-server devices" -- proves the architecture is not Redfish-locked |

**Exit criteria (mandatory):** A single-machine deployment runs Agent + SM + CC + required backing services, connects to a simulator or supported device, executes the complete Observe -> Reason -> Authorize -> Act -> Verify -> Outcome flow, survives service restart, and exposes sufficient health/metrics to diagnose failures.

Grafana visualization is useful but not the primary success metric. The end-to-end operational loop is the exit gate.

**Does NOT include:** New features, new device protocols, new UI screens, air-gapped LLM. R4-0 is validation of what exists.

### R4-1: Infrastructure Breadth

**Objective:** Prove HarkenIQ works beyond Redfish servers by shipping one non-Redfish protocol implementation.

**Scope:**

| Item | Why |
|---|---|
| IPMI protocol implementation (`IPMIProtocol`) | Proves DeviceProtocol abstraction works; widest BMC support; easiest testing (OpenIPMI simulator) |
| IPMI sensor normalization -> NormalizedDevice | Same skill files evaluate IPMI data identically to Redfish |
| IPMI action execution (IDENTIFY_LED, SEL_CLEAR via ipmitool) | Proves action model is protocol-agnostic |
| Config-level protocol selection (`bmc.protocol: ipmi`) | Backward-compatible; Redfish remains default |
| Cross-site correlation logic (R-C2) at CC | Multi-site pattern matching on outcome data; builds on R3b-3 PatternDetector |
| Vendor reliability comparison UI at Console | Analytics dashboard on existing aggregated outcome data; uses R3b-3 OutcomeAggregator |

**Exit criteria:** Agent configured with `protocol: ipmi` passes all existing skill tests. Cross-site pattern detection identifies batch failures spanning 2+ sites.

### R4-2: Fleet Intelligence

**Objective:** Make the CC genuinely intelligent -- predictive, compliance-aware, and integration-ready.

**Scope:**

| Item | Why |
|---|---|
| Compliance-grade audit (SHA-256 hash chain across all services) | SOC2/ISO27001 requirement for regulated segment |
| Config compliance detection + auto-remediation playbooks | Extends R3b-3 playbook model to config drift correction |
| Firmware inventory collection + CVE exposure scanning | Agent reports firmware versions; CC matches against known CVEs |
| Warranty/lifecycle via vendor APIs (Dell TechDirect, HPE iLO Federation) | CC enriches fleet data with warranty status and EOL dates |

**Exit criteria:** Audit trail is cryptographically verifiable. Config drift detected and corrected via playbook. Fleet dashboard shows warranty status per device.

### R4-3: Governance and Ecosystem

**Objective:** Enable the platform ecosystem -- marketplace, air-gapped deployments, predictive maintenance.

**Scope:**

| Item | Why |
|---|---|
| Community skill marketplace (submission, review, installation) | Network effects; customer-contributed detection improvements |
| Full air-gapped LLM serving (local model at SM) | Sovereign deployment requirement; government/defense segment |
| Firmware update orchestration (staged, blast-radius-aware) | Highest-risk capability; requires extensive testing |
| Predictive maintenance (ML models on aggregated outcomes) | Requires 6+ months of outcome data accumulation |

**Exit criteria:** Marketplace has 10+ community skills reviewed and promoted. Air-gapped deployment runs with local LLM. Firmware orchestration tested with staged rollout and rollback.

### Boundary Validation

**Why this split, not another:**

1. **R4-0 before R4-1:** You cannot validate IPMI support on a system that cannot be deployed. Production hardening is the foundation.

2. **R4-1 before R4-2:** Cross-site correlation and vendor reliability are the highest-value CC features for design partners. They require the least new infrastructure (just logic on existing data).

3. **R4-2 before R4-3:** Compliance audit and config remediation are selling features for regulated customers. Marketplace and air-gapped LLM are ecosystem plays that take longer to mature.

4. **IPMI in R4-1, not gNMI:** IPMI has the widest BMC support (every Dell/HPE/Lenovo server), easiest testing (OpenIPMI simulator available), and moderate complexity (~1000 LOC). gNMI is richer but more complex (YANG models, gRPC bindings, vendor-specific deviations). IPMI validates the abstraction; gNMI can follow in R4-2 or R5.

**Challenge: should R4-2 and R4-3 merge?** No. Firmware orchestration is the highest-risk capability in the entire platform (bricked device = permanent hardware loss). It needs dedicated attention, not bundling with marketplace or LLM work. Keeping it in R4-3 gives it the longest testing runway. Firmware orchestration must be treated as a controlled lifecycle capability with its own staged rollout and safety design, not as an ordinary action.

**Boundary flexibility:** These boundaries are not rigid waterfalls. R4-0 is a hard prerequisite for everything. R4-1 through R4-3 have internal parallelism where capabilities are independent. Fleet intelligence (R4-2) builds on the existing CC learning/outcome pipeline (R3b-3) rather than creating a parallel intelligence path.

**Air-gapped LLM timing:** Not a mandatory R4-0 requirement. During R4-1, validate that the existing LLMProvider can run against a local OpenAI-compatible or llama.cpp-based endpoint without changing application logic. Full sovereign packaging (model lifecycle, GPU sizing, disconnected deployment) remains a later dedicated milestone. This gives early architectural validation without prematurely turning HarkenIQ into a sovereign deployment project.

## 6. Device Extensibility Investigation (OQ-16)

### Current Redfish coupling

| Component | Redfish-coupled? | Protocol-agnostic? |
|---|---|---|
| `redfish/client.py` (transport) | 100% | Replaced by DeviceTransport |
| `redfish/discovery.py` (identity) | 100% | Replaced by DeviceDiscovery |
| `redfish/dell.py`, `hpe.py` (normalizers) | 100% | Moved into RedfishProtocol |
| `redfish/normalize.py` (data models) | 0% | Already abstract |
| `poller.py` (orchestration) | 30% | Refactored to use DeviceProtocol |
| `skills/engine.py` | 0% | No change needed |
| `autonomy/diagnosis.py` | 0% | No change needed |
| `actions/executor.py` | 50% | Action dispatch via DeviceProtocol |

**Key finding:** 63% of the codebase (1400 LOC) is already protocol-agnostic. The abstraction boundary is clean.

### DeviceProtocol interface

```python
class DeviceProtocol(Protocol):
    async def connect(self, credentials: dict) -> None: ...
    async def disconnect(self) -> None: ...
    async def detect_identity(self) -> DeviceIdentity: ...
    async def poll_sensors(self) -> NormalizedDevice: ...
    async def execute_action(self, action: Action) -> ActionOutcome: ...
    @property
    def name(self) -> str: ...  # "redfish" | "ipmi" | "gnmi"
```

### DeviceProtocol contract notes

- **Lifecycle:** Poller owns `connect()` and `disconnect()` calls. Protocol implementations must be stateless between polls (no cached sessions that could stale).
- **Errors:** `connect()` raises `ConnectionError` on auth failure, `TimeoutError` on network unreachable. `poll_sensors()` raises `ProtocolError` on malformed response. All are subclasses of `HarkenIQError`.
- **Idempotency:** `poll_sensors()` must be idempotent and safe to call at any frequency. `execute_action()` may have side effects (it's an action).
- **Credentials:** Passed via `connect(credentials: dict)`. Credential refresh is the Poller's responsibility (calls `CredentialProvider` before each `connect()` if TTL expired).

### Protocol comparison for first proof point

| Protocol | Telemetry | Actions | Auth | Testability | Effort | Recommendation |
|---|---|---|---|---|---|---|
| **IPMI** | Rich sensor data | LED, SEL, chassis | Simple (user/pass) | OpenIPMI simulator | ~1000 LOC | **First** |
| gNMI | Streaming, YANG models | Config modify | TLS certs, JWT | Limited simulators | ~1100 LOC | Second |
| NETCONF | XML, structured | Config edit | SSH keys | vMX/CSR1000v | ~1000 LOC | Third |
| SNMP | Good, fragmented MIBs | Limited | SNMPv3 auth | snmpsim | ~800 LOC | Alternative to IPMI |
| SSH CLI | Vendor-specific | Vendor commands | SSH keys | Requires mocking | ~600 LOC | Not recommended |

**Decision: IPMI first for server BMC extensibility.** Widest server BMC support. Every Dell/HPE/Lenovo server supports IPMI. OpenIPMI simulator available for CI. Validates the DeviceProtocol abstraction without YANG/gRPC complexity. Uses IPMI-over-LAN (RMCP+ UDP port 623) via `pyghmi` Python library -- no `ipmitool` binary, no root required (preserves doc 06 contract: "No root required").

**Note:** IPMI validates server BMC protocol extensibility only. It does NOT satisfy or replace the future network-device monitoring requirement (gNMI/NETCONF for switches/routers), which remains a separate capability deferred to R4-2 or R5.

**Architecture guarantee:** The DeviceProtocol abstraction MUST ensure that adding gNMI or NETCONF later does not require changes to the reasoning, autonomy, skills, playbooks, or fleet-learning layers. If the IPMI proof point reveals coupling in any of these layers, that coupling must be fixed before R4-1 exits.

## 7. Air-Gapped LLM Investigation (OQ-18)

### Workload analysis (define the work before choosing the tool)

| LLM Use Case | Current Location | Calls/Day (50 servers) | Latency Tolerance | Context Size | Concurrency |
|---|---|---|---|---|---|
| Incident explanation (LLM Explain) | SM | ~5-20 (on new incidents) | 30s acceptable | ~2000 tokens (incident + evidence) | 1 (serial per incident) |
| Candidate skill generation | SM | ~1-5 (novel resolutions) | 60s acceptable | ~3000 tokens (diagnosis + action + YAML) | 1 |
| Fleet pattern interpretation | CC | ~1-3 (on new patterns) | 120s acceptable | ~1500 tokens | 1 |

**Key finding:** The workload is light. 5-20 calls per day, serial execution, 30-120s latency tolerance. This is not a high-throughput inference workload.

### Model selection criteria

| Criterion | Requirement |
|---|---|
| Context window | >= 4096 tokens (incident context is ~2000 tokens) |
| Output quality | Must produce valid YAML for skill generation; must produce coherent English for explanation |
| Memory footprint | <= 8GB VRAM (fits commodity GPU or CPU-only inference) |
| License | Permissive (Apache 2.0 or similar); no phone-home requirement |
| Update mechanism | Model files copied via USB/offline transfer; no internet dependency |

### Candidate models (as of 2026-08-24)

| Model | Parameters | VRAM | License | Quality for HarkenIQ Use Cases |
|---|---|---|---|---|
| Llama 3.1 8B | 8B | 6-8GB (Q4) | Meta Community | Good for explanation; adequate for YAML |
| Mistral 7B v0.3 | 7B | 5-7GB (Q4) | Apache 2.0 | Good for structured output (YAML) |
| Phi-3 Mini 3.8B | 3.8B | 3-4GB (Q4) | MIT | Adequate; smaller context window |
| Gemma 2 9B | 9B | 7-9GB (Q4) | Google permissive | Strong reasoning |

### Deployment model

```
Site Manager (air-gapped)
  |
  +-- LLMProvider (existing interface)
  |     |
  |     +-- Connected mode: httpx -> cloud API (unchanged)
  |     +-- Air-gapped mode: httpx -> localhost:8080 (local inference server)
  |
  +-- Local Inference Server (new)
        |
        +-- llama.cpp server (C++, no Python deps)
        +-- OR vLLM (Python, higher throughput)
        +-- Model file: /opt/harkeniq/models/mistral-7b-v0.3.Q4_K_M.gguf
        +-- Config: context_size=4096, threads=4, gpu_layers=auto
```

**Key design decision:** The `LLMProvider` interface already works with any OpenAI-compatible `/chat/completions` endpoint. `llama.cpp` server exposes exactly this API. No code change needed at SM. The only new component is the inference server deployment (Docker container + model file).

**GPU floor:** 6GB VRAM minimum (NVIDIA T4 or equivalent). CPU-only inference is possible but 10x slower (acceptable for 5-20 calls/day).

**Model management (air-gapped):** Model files are SHA-256 checksummed at build time. SM validates checksum on startup and rejects corrupted files. Model metadata (name, version, checksum, quantization) reported in SM health endpoint. Model update is an explicit operator action (copy file, restart SM), not automatic. No phone-home, no auto-download.

### End-to-end validation scenario

1. `docker compose up` starts all services
2. Agent registers with SM (gRPC RegisterAgent + identity bootstrap)
3. Agent polls mock simulator (Redfish), detects healthy baseline
4. Operator injects fault via mock simulator API (`/test/inject-fault`)
5. Agent detects fault, proposes action (ReportVerdict + ReportAction)
6. CC polls SM, shows pending action in fleet dashboard
7. Operator approves via Console UI (or CC API)
8. Agent executes action, reports outcome
9. Outcome appears in CC outcome history
10. Grafana dashboard shows the full cycle

**This scenario exercises every layer and every gRPC RPC.** If this works end-to-end, R1-R3b is validated as an integrated platform.
