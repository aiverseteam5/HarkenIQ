## Problem Statement

Every data center runs mixed hardware. No vendor's tool sees another vendor's boxes. Above the hardware, AI SRE tools reason about applications and software -- none of them touch the physical machines. Between those two layers sits a gap filled by humans doing toil: watching six consoles, chasing symptoms across layers, doing the same repetitive fixes at 2am.

The current triage workflow has 10+ hops between hardware fault and fix:
Redfish API -> Prometheus -> Grafana (GEM+GEL) -> PostgreSQL -> incident queue -> L1 reads SOP -> triages to L2 -> L2 waits hours -> logs in via Teleport -> reads logs -> Teams discussion -> figures out it's a service restart or config change.

Too many layers. Knowledge gaps on every hardware type. Unnecessary complexity between the alert and the fix.

HarkenIQ is not a monitoring tool. It is an autonomous operations platform with distributed intelligence -- an embedded brain on every device that observes, reasons, acts, and learns. The IoT model inverts the conventional "centralize everything into one dashboard" approach: intelligence is distributed TO each device, collapsing the 10-hop triage chain to 1-2 hops.

## Demand Evidence

- **Founder-as-customer:** 20 years of data center management experience (legacy Windows servers, AD, virtualization, VMware, VxRail, HCI, AWS, Azure, GPU, HPC, Cyber Recovery, GPU/AI infrastructure). The founder IS the target user and has lived the pain firsthand.
- **No external validation yet.** The PRD's Section 15 acknowledges this honestly: "Everything above is hypothesis until real operators confirm it." Kill criterion: if hardware toil isn't top-3 pain for at least 3 of 5 mixed-fleet operators, the beachhead is wrong.
- **Category validation exists.** AI SRE startups (Resolve AI, Cleric, NeuBird) have proven enterprises budget for AI that operates production. One player is valued above $1B. None touch hardware.
- **Structural advantage:** A vendor's fleet tool ultimately serves the vendor. A neutral brain serves only the fleet owner -- including telling them honestly which vendor's hardware fails more. That feature can never ship from a vendor.

## Status Quo

The founder described the current workflow from direct operational experience:

1. **Hardware alerts** exported from Redfish API, configured through Prometheus
2. **Grafana dashboards** (GEM + GEL stack) for visualization
3. **PostgreSQL** to save evidence and historical data
4. **Alerting rules** create incidents, sent to support queues
5. **L1 manual intervention** -- reads SOPs, checks known issues, triages to L2
6. **L2 engineer** (hours later) -- logs into the system via Teleport, reads logs
7. **Collaboration** -- Teams channel discussion to determine if it's a bug or config issue
8. **Resolution** -- often a simple service restart, config change, or known fix
9. **Front-end reporting layer** pulls data from Prometheus, pushes to Azure Airflow, data pump to front-end for reporting

**The status quo's real cost:** too many layers, knowledge gaps on every hardware type in the platform, unnecessarily complex layering between the actual hardware and the humans who fix it. Every new hardware vendor adds another console to juggle, another API to learn, another set of tribal knowledge to maintain.

**The real competitor** is not Datadog or CloudIQ -- it's this cobbled-together workflow that operators have normalized as "just how things work."

## Target User & Narrowest Wedge

**Primary user:** The L2 infrastructure engineer at any organization running mixed-fleet hardware. 5-person ops team managing 100+ devices across vendors. Gets paged at 2am. Spends hours triaging whether a failure is hardware or software. Keeps tribal knowledge in their head or a spreadsheet.

**Beachhead segment:** Any organization managing data center hardware across multiple vendors -- enterprises, GPU cloud operators, AI factories, HPC centers, colocation providers, and sovereign/regulated data centers. The common thread: mixed fleets with Redfish-capable hardware (Dell, HPE, Lenovo, Supermicro, OpenBMC), where hardware toil scales with fleet size. HarkenIQ can specialize for GPU/AI/HPC workloads but the platform manages ALL hardware device types.

**The three people in every deal:**
- **Ops engineer / SRE** -- adopts. Installs the agent, becomes the champion.
- **Head of Infrastructure / VP** -- pays. Cares about two numbers: engineers saved and downtime prevented.
- **Security & Compliance** -- blocks. Cannot say yes, can absolutely say no. Wins with: read-only start, everything signed, full audit trail, their own approval gates.

**Narrowest wedge:** A single CLI agent that auto-detects hardware vendor via Redfish, runs 5 cross-vendor health checks (fan, disk, memory, PSU, thermal), and returns structured verdicts: OK, ACTION_NEEDED (with specific fix), or ESCALATE. Install in minutes. The "wow demo": one physical fault explained as the root cause of application-layer symptoms.

## Premises

1. **Hardware toil is top-3 pain** worth premium pricing -- not just "annoying" but a budget-line problem.
2. **The embedded-agent (IoT) architecture is the product**, not just an implementation choice. Distributing intelligence to each device is the moat. The agent is a full operations endpoint -- not a poller, not a monitor -- capable of executing skills, managing credentials, and taking remediation actions with configurable approval gates.
3. **Any organization with mixed-fleet Redfish-capable hardware is the market** -- enterprises, GPU cloud, AI factories, HPC, colocation, sovereign data centers. The platform manages all hardware; specialization (GPU/AI/HPC) is a skill-set overlay, not a market constraint.
4. **Free Observe agent is distribution; paid = action.** The line between free and paid is visibility vs. remediation capability.
5. **Credential custody + rotation turns the trust objection into a feature.** The "keys to every machine" objection is the deal-killer; the co-founder's identity management depth is the structural answer.
6. **A 4-person team can ship MVP in 30 days and validate by day 60** using agent-driven development.

## Approaches Considered

### Approach A: Monolith-to-Platform
Start with Agent + Site Manager as a single deployable. Skills as YAML in a git repo. SQLite for local data. Extract services as you scale.
- **Effort:** S to start, XL to scale
- **Risk:** Low early, high later (re-architecture debt at ~100 customers)
- **Pros:** Fastest to ship. Easiest to iterate. Learn what matters before over-engineering.
- **Cons:** Technical debt accumulates. Re-architecture is painful mid-growth. Doesn't model the real product architecture.

### Approach B: Three-Tier from Day 1
Build Agent, Site Manager, Cluster Manager as separate components with clean APIs (gRPC/NATS) from the start. Skill catalog as a versioned registry. Matches the stated product vision directly.
- **Effort:** M to start, L to scale
- **Risk:** Medium (more upfront, but clean growth path)
- **Pros:** Architecture matches the product vision. No re-architecture needed. Clean separation enables on-prem vs. cloud deployment flexibility. Each tier can scale independently.
- **Cons:** Slower to first demo. More infrastructure to manage early.

### Approach C: Agent-Heavy Mesh
Maximum intelligence in the agent. Agents operate fully offline, coordinate peer-to-peer at a site. Site Manager is thin -- oversight and UI only.
- **Effort:** L to start, M to scale
- **Risk:** High (distributed systems complexity, harder to update and debug)
- **Pros:** Maximum resilience for air-gapped environments. Agents are self-sufficient.
- **Cons:** Peer-to-peer coordination is the hardest distributed systems problem. Debugging fleet-wide issues across independent agents is painful.

## Recommended Approach

**Approach B: Three-Tier from Day 1** -- because the product IS the architecture. The three tiers (Agent, Site Manager, Cluster Manager) map directly to the product's value proposition, pricing model, and trust ladder. Starting with the right architecture avoids the re-architecture tax that kills velocity at the worst possible time (post-design-partner, pre-scale).

## Full Platform Architecture

### Tier 1: HarkenIQ Agent (Endpoint Brain)

A thin, lightweight agent installed on every managed device. The agent is analogous to Symantec Altiris endpoint agents but with embedded intelligence.

**Core capabilities:**
- **Hardware discovery:** Auto-detect vendor and model from Redfish `/redfish/v1/` root. Support Dell iDRAC, HPE iLO, Lenovo XCC, Supermicro BMC, and extensible to any Redfish-compliant hardware.
- **Telemetry collection:** Continuous collection from Redfish API -- health state, sensor readings, event logs, firmware versions, configuration. Also local OS-level metrics: CPU, memory, disk, GPU utilization, driver state, process health.
- **Anomaly detection:** Local pattern matching against known failure signatures. Pre-failure detection for disks (SMART), memory (ECC error rates), fans (RPM degradation), PSU (voltage drift), GPU (thermal throttling, NVLink errors).
- **Skill execution:** Run deterministic skill files received from Site Manager. Skills define: condition (JSONPath against Redfish/local data), action (Redfish PATCH, shell command, API call), rollback (pre-action snapshot + undo command), and approval requirement (auto/manual/never).
- **LLM escalation:** When no skill matches, package the anomaly context (device state, recent events, similar past incidents) and escalate to Site Manager for LLM-assisted reasoning. LLM responses are validated before surfacing: proposed actions must reference real Redfish endpoints on the target device, confidence below 60% defaults to ESCALATE-to-human rather than proposing an action, and LLM calls have a 30-second timeout with fallback to "ESCALATE: LLM unavailable." Air-gapped deployments without LLM access operate on deterministic skills only; novel situations are escalated to human operators directly.
- **Credential handling:** Just-in-time credential fetching. The agent's internal Credential Broker component makes a request to the Site Manager's Credential Proxy, which fetches the credential from the configured vault (HashiCorp Vault, CyberArk) on the agent's behalf. The agent never connects directly to the vault -- all credential traffic is brokered through the Site Manager, which enforces policy (rate limiting, action-type authorization) before forwarding. Credentials are short-lived (5-minute TTL), used for the specific action, and discarded. Certificate-based mutual TLS for all agent-to-manager communication.
- **Heartbeat and health:** Regular heartbeat to Site Manager with agent health, current skill versions, pending actions, and device state summary.
- **Offline operation:** If Site Manager is unreachable, agent continues observing and executing locally-cached skills within its autonomy budget. Queues events and outcomes for sync when connectivity restores.

### Tier 2: Site Manager (Site Intelligence Hub)

One per data center site. Coordinates all agents at that site, provides the operator interface, hosts the skill registry, and runs the reasoning engine.

**Core capabilities:**
- **Agent fleet management:** Registration, health monitoring, skill distribution, version management, rolling updates. Canary deployment of new skills (deploy to 1 agent, verify, expand to 10%, then full fleet).
- **Skill registry:** Versioned catalog of all skills. Git-backed. Each skill has: metadata (vendor, device type, severity, action type), condition definition, action definition, rollback definition, approval requirement, test cases, and deployment history.
- **Reasoning engine:** When an agent escalates, the Site Manager runs cross-device correlation (is this a single device or a pattern?), checks the knowledge base (has this been seen before?), and if needed, invokes the LLM for novel situation analysis.
- **Approval workflow:** Queue of proposed actions from agents. Each action shows: what device, what's wrong (evidence), what the proposed fix is, what the rollback is, confidence level, and impact assessment. Operator approves/denies from dashboard, Slack, or CLI.
- **Integration gateway:** Connects to external systems:
  - **HashiCorp Vault / CyberArk** -- credential management and password rotation
  - **GitLab / GitHub** -- documentation, RCA records, change plans, skill version control
  - **Slack / Teams / PagerDuty** -- approval notifications, incident alerts
  - **ServiceNow / Jira** -- outbound incident/change records (not ITIL workflow -- just evidence recording)
  - **Prometheus / Grafana** -- export metrics for operators who want to keep their existing dashboards
- **Knowledge base:** PostgreSQL with full-text search (pg_trgm for similarity matching). Stores:
  - Past incidents and resolutions (searchable by device type, symptom, root cause)
  - RCA templates and completed analyses
  - Vendor documentation references
  - Skill execution history and outcomes
  Semantic search (vector embeddings) deferred to post-MVP when the knowledge base has enough entries to benefit from it.
- **Audit engine:** Every observation, proposed action, approval/denial, execution, and outcome is logged with cryptographic signing. Immutable audit trail. Exportable for compliance (SOC2, ISO 27001).
- **Operator dashboard (web UI):**
  - Fleet overview: all agents, health state, pending actions, recent outcomes
  - Device drill-down: individual device history, current state, active skills
  - Approval queue: proposed actions with evidence, one-click approve/deny
  - Skill management: browse catalog, deploy/rollback skills, view test results
  - Analytics: toil hours recovered, incidents auto-resolved, MTTR trends
  - Settings: approval policies, autonomy budgets, integration configuration

### Tier 3: Cluster Manager (Global Control Plane)

Manages multiple Site Managers across locations. Provides the VP/NOC-level view and global policy management.

**Core capabilities:**
- **Multi-site federation:** Aggregate fleet state across all sites. Cross-site pattern recognition (is this failing DIMM batch affecting all sites, or just one?).
- **Global skill catalog:** Master skill registry. Skills authored and tested centrally, distributed to Site Managers. Community-contributed skills reviewed and promoted here.
- **Policy management:** Global approval policies, autonomy budgets per site/device-type/action-type. Role-based access control (RBAC) -- who can approve what, at which sites.
- **Compliance reporting:** Cross-site compliance evidence. Automated report generation for SOC2, ISO 27001 audits. Data residency controls (which data stays at which site).
- **Analytics and intelligence:** Cross-fleet trends. Vendor reliability comparisons (the "neutral" value prop -- which vendor's hardware fails more). Predictive maintenance models trained on fleet-wide data.
- **API gateway:** REST/gRPC APIs for:
  - Third-party integrations
  - Custom automation and scripting
  - Reporting and BI tools
  - Customer-built workflows

**Deployment options (customer's choice):**
- **Fully on-prem:** All three tiers on customer infrastructure. LLM runs on-prem (open-source model or customer's GPU allocation). Zero data leaves the customer's network. Required for air-gapped/sovereign sites.
- **Hybrid:** Agents and Site Manager on customer infra. Cluster Manager in HarkenIQ cloud. LLM via cloud API. Simpler to operate, data sovereignty controls for sensitive telemetry.

## The Learning Loop: Observe -> Reason -> Act -> Learn

The learning loop is HarkenIQ's core differentiator. It transforms the platform from a playbook executor into a continuously improving autonomous operations system.

### Observe
- **Continuous telemetry:** Redfish API polling (configurable interval, default 60s), local OS metrics, GPU state (nvidia-smi, NVLink health), storage controller state, network switch port status.
- **Event stream:** Real-time event capture from Redfish event subscriptions (SSE), syslog, kernel messages, hardware event logs.
- **Baseline modeling:** Per-device behavioral baseline established during the first 7 days. Anomalies are deviations from the device's own normal, not fixed thresholds.
- **Cross-device correlation:** Site Manager correlates anomalies across devices. A single fan failure is local. Ten fan failures in the same rack in the same hour suggests environmental (cooling system, not hardware).

### Reason
- **Tier 1 (Agent, local):** Pattern match against skill file conditions. Confidence is computed as the percentage of a skill's condition checks that match (e.g., 4 of 5 conditions matched = 80%). If all conditions match (100%), proceed to Act. If partial match (60-99%), escalate to Site Manager for cross-device correlation before acting. Below 60%, skip the skill. This handles 70-80% of routine issues without any network call.
- **Tier 2 (Site Manager, site-wide):** Cross-device correlation, knowledge base lookup, historical pattern matching. If a similar incident was resolved before, propose the same fix with the prior evidence.
- **Tier 3 (LLM, novel situations):** Package the full context (device state, recent events, similar past incidents, vendor documentation) and query the LLM. The LLM proposes a diagnosis and suggested actions. LLM output is ALWAYS treated as a proposal -- never auto-executed without validation.
- **Root cause analysis:** When an application-layer symptom correlates with a hardware-layer event (the "cross-layer cause-to-symptom correlation" from the PRD), the system generates a structured RCA linking the physical fault to the application impact. This is the "wow demo."

### Act
- **Approval model (configurable per customer, per action type, per device type):**
  - **Auto-approve:** For proven, low-risk actions on non-critical devices. E.g., log rotation on a monitoring server.
  - **Request approval:** For standard remediation. Action proposed with evidence, operator approves in ~15 seconds from Slack/dashboard.
  - **Require dual approval:** For high-impact actions (firmware upgrade, configuration change on production GPU nodes). Two named humans must approve.
  - **Never auto-act:** Customer can configure any action type to always require approval. One-command stop switch disables all autonomous actions fleet-wide.
- **Action execution:** Pre-action state snapshot (for rollback). Execute via Redfish PATCH, shell command, API call. Post-action verification (did the fix work? did new symptoms appear?).
- **Blast radius control:** Rate limiter prevents any skill from executing on more than N devices simultaneously (configurable, default: 1 device for new skills, 10% of fleet for proven skills). Automatic halt if failure rate exceeds threshold.
- **Rollback capability:** Actions categorized as reversible or one-way. Reversible actions have automatic rollback if post-action verification fails. One-way actions (firmware upgrade) require explicit approval and have no automatic rollback.

### Learn
- **Outcome tracking:** Every action is recorded with its outcome (success, partial, failure, rollback triggered). Linked to the original anomaly, the reasoning path, and the approval chain.
- **Skill refinement:** When an operator corrects or overrides a proposed action, the correction is captured as training data. Over time, skill conditions are refined to match operator judgment.
- **Auto-skill generation:** When the LLM successfully diagnoses and resolves a novel situation (confirmed by post-action verification), the system generates a candidate skill file. The candidate goes through the skill validation pipeline (see below) before it can be deployed.
- **Fleet-wide pattern learning:** Cluster Manager aggregates outcomes across sites. If a specific DIMM part number shows correlated failures across the fleet, this becomes a proactive alert for all sites with that part number (Google SRE "proactive paths" model).
- **Error budget model (Google SRE):** Each action type has an error budget. If the system's auto-resolved actions have a failure rate above threshold (configurable, default 5%), it automatically drops from Act to Approve mode for that action type until the error budget recovers. Self-regulating trust.

### Key Definitions

- **Autonomy budget:** The maximum number and severity of actions an agent or site can auto-execute within a time window without human approval. Configured per action-type, per device-type, per time-period. Example: "max 5 auto-restarts per device per day, max 1 firmware update per site per week." When the budget is exhausted, all actions of that type require explicit human approval until the window resets. The autonomy budget is the primary safety mechanism preventing runaway automation.

- **Composite action:** A skill action type consisting of an ordered sequence of sub-actions that must all succeed. Example: "stop service -> apply config change -> verify config -> restart service." If any step fails, the remaining steps are skipped and rollback begins from the last successful step. Composite actions are atomic from an approval perspective -- the operator approves the entire sequence, not individual steps.

## Skill Architecture

### Skill File Format (YAML)

```yaml
skill:
  id: "dell-idrac-fan-failure-remediation"
  version: "1.2.0"
  vendor: "dell"
  device_types: ["poweredge-r750", "poweredge-r760"]
  category: "thermal"
  severity: "warning"
  tier: "core"  # core | vendor | community | auto-generated

condition:
  # JSONPath expressions against Redfish data
  checks:
    - path: "$.Thermal.Fans[*].Status.Health"
      operator: "contains"
      value: "Critical"
    - path: "$.Thermal.Fans[*].Reading"
      operator: "less_than"
      value: 1000  # RPM threshold

evidence:
  collect:
    - redfish: "/redfish/v1/Chassis/1/Thermal"
    - redfish: "/redfish/v1/Systems/1/LogServices/Sel/Entries"
    - command: "ipmitool sensor list | grep -i fan"

action:
  type: "redfish_patch"  # redfish_patch | shell | api_call | composite
  approval: "request"     # auto | request | dual | never
  reversible: true
  steps:
    - description: "Clear fan fault via Redfish (vendor-specific OEM action where available, otherwise log-and-alert)"
      method: "POST"
      target: "/redfish/v1/Chassis/1/Actions/Oem/DellOemChassis.ClearFanFault"
      fallback: "alert_operator"
      note: "Full chassis reset (Chassis.Reset) is disproportionate for a fan fault and may reboot the host. Use vendor-specific OEM endpoints where available. If no OEM endpoint exists, alert the operator instead of resetting."
  rollback:
    steps:
      - description: "No automated rollback -- fan fault clearance is idempotent"
        action: "none"

verification:
  wait_seconds: 60
  checks:
    - path: "$.Thermal.Fans[*].Status.Health"
      operator: "equals"
      value: "OK"
    - path: "$.Thermal.Fans[*].Reading"
      operator: "greater_than"
      value: 3000

dependencies: []  # skill IDs that must run first
blast_radius:
  max_concurrent: 1
  cooldown_seconds: 300

metadata:
  author: "harkeniq-core"
  tested_firmware: ["2.82.82.82", "2.83.83.83"]
  test_cases: ["tests/dell-fan-failure.yaml"]
  created: "2026-07-15"
  last_verified: "2026-07-27"
```

### Skill Tiers

1. **Core skills** (built by HarkenIQ team): Cross-vendor Redfish-standard operations. Work on ANY Redfish-compliant hardware. Initial set: fan failure, disk predictive failure (SMART), memory ECC error, PSU degraded, CPU thermal throttle, NVLink error, GPU memory ECC, storage controller degraded.

2. **Vendor skills** (built by HarkenIQ team + community): Vendor-specific operations beyond Redfish standard. Dell iDRAC-specific, HPE iLO-specific, Lenovo XCC-specific, Cisco switch-specific, Brocade SAN-specific, NetApp storage-specific, Nutanix HCI-specific, PowerScale/PowerStore-specific.

3. **Community skills** (open-source contributions): Operators contribute skills for hardware they manage. Reviewed by HarkenIQ team before promotion to the shared catalog. The open-source flywheel: community extends coverage to hardware HarkenIQ will never own.

4. **Auto-generated skills** (LLM-created): When the system encounters unknown hardware, the LLM researches the vendor's Redfish implementation, drafts a candidate skill. Candidate skills enter the validation pipeline and are flagged as "auto-generated, confidence: N/10" until manually reviewed.

### Skill Validation Pipeline

```
Author/LLM generates skill
        |
        v
  Static analysis (YAML schema, safety checks)
        |
        v
  Dry-run on target device (no-op, verify condition matching)
        |
        v
  Sandbox execution (single non-production device if available)
        |
        v
  Canary deployment (1 device, monitored for 24h)
        |
        v
  Graduated rollout (10% -> 50% -> 100%, with automatic halt on failure)
        |
        v
  Promoted to catalog (versioned, tested, documented)
```

### Skill Distribution

Site Manager pulls skills from Cluster Manager's global catalog (or from a local git repo in air-gapped deployments). Skills are versioned and deployed to agents on-demand or on schedule. Agents pull skill updates from Site Manager at configurable intervals (default: every 5 minutes). Skill rollback is instant -- Site Manager pushes the previous version to affected agents.

## Security Architecture

### Trust Model

```
Agent <--mTLS--> Site Manager <--mTLS--> Cluster Manager
                      |                       |
                      v                       v
                 Vault/CyberArk          Policy Engine
                 (Credential Proxy)      (RBAC, budgets)
                      |
                      v
                 Audit Store
                 (signed logs)
```

Note: Agent never connects directly to Vault/CyberArk. All credential requests are brokered through Site Manager's Credential Proxy.

- **Agent attestation:** New agents present a signed installation token (generated by Site Manager during provisioning). Mutual TLS with client certificates for ongoing communication. Agent binaries are signed and verified at startup (tamper detection).
- **Just-in-time credentials:** Agent NEVER stores hardware credentials (iDRAC/iLO passwords). When an action requires hardware access, agent requests a short-lived credential from the configured vault (Vault/CyberArk) via Site Manager's credential broker. Credential is used once and discarded. Blast radius: a compromised agent cannot access other machines because it holds no credentials.
- **Password rotation:** Automated rotation of hardware BMC passwords on a configurable schedule. Rotation is itself a skill file. New passwords stored in vault, old passwords invalidated. This is a sellable feature -- most operators don't rotate BMC passwords because it's manual toil across hundreds of devices.
- **Audit trail:** Every observation, proposed action, approval, execution, and outcome is logged with:
  - Timestamp (NTP-synchronized)
  - Agent identity (certificate fingerprint)
  - Device identity (serial number, BMC MAC)
  - Action details and evidence
  - Approver identity (for approved actions)
  - Cryptographic signature (SHA-256 HMAC chain)
- **Compliance evidence engine:** Automated generation of compliance artifacts. SOC2 Type II evidence packages. ISO 27001 control mapping. Exportable audit logs in standard formats (CEF, JSON, STIX).

### Agent Security

- Agent runs as a dedicated `harkeniq` service user with specific Linux capabilities: `CAP_NET_RAW` (for IPMI/ipmitool), `CAP_DAC_READ_SEARCH` (for reading hardware logs). GPU metrics (`nvidia-smi`) require the `video` group. Actions requiring elevated privileges (certain Redfish operations, firmware updates) execute through a minimal privileged helper process (`harkeniq-exec`) that accepts only structured action requests from the agent via a Unix socket -- never arbitrary commands.
- Sandboxed execution environment for skill actions
- Rate-limited API access to prevent abuse
- Automatic quarantine if agent behavior deviates from expected patterns (e.g., excessive Redfish requests, unexpected network connections)

### Installation
- **One-liner install:** `curl -sSL https://get.harkeniq.com | sh -s -- --site-manager <SM_URL> --token <PROVISION_TOKEN>`
- **Automated provisioning:** Ansible/Salt/Puppet modules for fleet-wide deployment
- **PXE integration:** Agent pre-installed in PXE boot images for new hardware provisioning
- **Container option:** Agent as a container for environments that prefer containerized management
- **Install time target:** Under 5 minutes for a single device, including registration with Site Manager

### Updates
- **Rolling updates:** Site Manager pushes agent updates in waves. Default: 5% of fleet -> wait 30 min -> 25% -> wait 1h -> 100%.
- **Automatic rollback:** If updated agents show degraded health within the monitoring window, automatically rollback to the previous version.
- **Version pinning:** Operators can pin specific devices or device groups to a specific agent version.
- **Skill updates are independent of agent updates.** Skills are hot-reloaded without agent restart.

### Health Monitoring
- **Heartbeat:** Agent sends heartbeat to Site Manager every 30 seconds (configurable). Heartbeat is lightweight (~200 bytes: agent health, version, pending action count). Telemetry collection runs on a separate 60-second cycle and pushes full device state. The heartbeat is intentionally more frequent than telemetry to detect agent/network failures quickly without the overhead of full telemetry on every cycle. At scale (10,000 agents = ~333 heartbeats/sec), Site Manager must handle this via async gRPC streaming with batched processing. Load testing target: Site Manager supports 10,000 agents on a single 4-core VM.
- **Silent agent detection:** If Site Manager doesn't receive heartbeat for 3 intervals (90s default), it distinguishes:
  - Network issue: try alternate communication path (if configured)
  - Agent crash or hardware down: alert operator with last-known device state and recommended diagnostic steps. Site Manager does NOT attempt direct BMC access -- the agent is the only component with brokered BMC credentials. Recovery from agent failure requires human intervention (SSH to the host, restart agent service, or physical inspection if hardware is down).
- **Self-healing agent:** Agent monitors its own health. Automatic restart on crash. Watchdog process ensures agent stays running.

### Platform Self-Management (Who Monitors the Monitor)
- **Site Manager HA:** Active-passive failover. Agents automatically fail over to secondary Site Manager. Shared state in replicated PostgreSQL.
- **Agent degraded mode:** If Site Manager is unreachable, agents continue:
  - Observing and logging locally (SQLite event store)
  - Executing cached skills within autonomy budget
  - NOT learning or updating skills
  - Sync queued events when connectivity restores
- **Cluster Manager resilience:** If Cluster Manager is unreachable, Site Managers operate independently. Cross-site correlation pauses but site-level operations continue.
- **Meta-monitoring:** HarkenIQ exposes its own health as Prometheus metrics. Operators can monitor the platform with their existing monitoring stack.

## Data Architecture

### Per-Agent (local)
- SQLite event store: observations, actions, outcomes (retained: 30 days default, configurable)
- Cached skill files (current versions)
- Device configuration snapshot (for rollback)

### Per-Site Manager
- PostgreSQL: agent registry, skill catalog, approval queue, knowledge base, audit log
- Time-series store (TimescaleDB or InfluxDB): telemetry metrics for trending and anomaly detection
- Document store: RCA records, vendor documentation references, change plans

### Per-Cluster Manager
- PostgreSQL: site registry, global policies, RBAC, compliance evidence
- Analytics store: aggregated fleet metrics, vendor comparison data, trend analysis
- Skill marketplace: global skill catalog, community contributions, test results

### Data Retention Policies
- **Agent (SQLite):** 30 days default, configurable. Oldest entries purged automatically.
- **Site Manager (PostgreSQL):** 1 year for telemetry/events, indefinite for audit trail and RCA records. Configurable per data type. Audit trail retention must meet compliance requirements (typically 7 years for SOC2).
- **Cluster Manager:** Aggregated metrics retained 2 years. Raw data stays at the Site Manager level and is not replicated to Cluster Manager.
- **All tiers:** Automated purge jobs run daily. Audit trail is append-only and never auto-purged -- purge requires explicit operator action with dual approval.

### Data Flow
```
Agent (SQLite) --gRPC--> Site Manager (PostgreSQL + TimescaleDB)
                              |
                         --gRPC--> Cluster Manager (PostgreSQL + Analytics)
                              |
                         --> External (Vault, GitLab, Slack, ServiceNow)
```

## Network Architecture

- **Agent -> Site Manager:** Agent initiates outbound gRPC connection on port 8443 (configurable). Agent dials out; no inbound ports required on the managed host. This is critical for firewall approval -- operators only open one outbound port per managed host.
- **Site Manager -> Cluster Manager:** Site Manager initiates outbound gRPC on port 9443. Same dial-out model.
- **Site Manager -> Vault/CyberArk:** Outbound HTTPS (port 443) to the customer's vault endpoint. Site Manager is the only component that communicates with the vault.
- **Site Manager -> External integrations:** Outbound HTTPS (port 443) to Slack, GitLab, ServiceNow, etc.
- **NAT/Proxy:** Agents support HTTP CONNECT proxy for environments where outbound connections go through a corporate proxy.
- **Air-gapped:** In disconnected environments, all communication stays within the site network. No external connections. Skill updates and agent updates delivered via local artifact repository.

## Open Questions

1. **Tech stack decision:** Python (faster to prototype, Redfish libraries exist) vs. Go (better for the agent binary, lower resource footprint, better cross-compilation)? Recommendation: Go for the agent, Python for Site Manager/Cluster Manager.
2. **LLM model selection:** Which LLM for reasoning? Cloud API (Claude/GPT) for connected deployments, open-source (Llama/Mistral) for air-gapped? Both?
3. **Skill file format:** YAML (human-readable, easy to author) vs. a DSL (more expressive, harder to learn)? Recommendation: YAML for v1.
4. **Open-source licensing:** Apache 2.0 for the agent (maximum adoption) vs. AGPL (forces contribution back)? Recommendation: Apache 2.0 for the agent, commercial license for Site Manager and Cluster Manager.
5. **US entity formation:** Where is the company registered? Required before first paid contract or pre-seed? Decision needed by day 45 per PRD.
6. **Design partner pipeline:** Do you have warm contacts at GPU cloud operators, or is this cold outreach? The second opinion's warning applies: your enterprise/HCI muscle memory may not match GPU cloud needs. You need to sit in their war room.
7. **Agent resource footprint:** How thin is thin? Target: <50MB memory, <1% CPU on the managed host. This constrains what the agent can do locally vs. what must be offloaded to Site Manager.
8. **Agent language for Phase 1:** The team's Go experience is unvalidated. Risk mitigation options: (a) build Phase 1 agent in Python for speed, rewrite in Go during Phase 2 once architecture is validated; (b) start in Go from day 7 but limit Phase 1 scope to 3 skills instead of 5; (c) confirm team Go proficiency before committing. Recommendation: option (a) -- Python for Phase 1, Go rewrite in Phase 2 -- because validating the product matters more than optimizing the binary.
9. **Redfish coverage reality:** Not all hardware exposes the same Redfish endpoints. Older firmware, cheaper hardware, and non-server devices (switches, storage) have varying Redfish support. How do you handle hardware with partial or no Redfish?
10. **Air-gapped LLM design:** Deferred to Phase 4. Phases 1-3 assume cloud LLM availability for connected deployments. Air-gapped deployments in Phases 1-3 operate without LLM reasoning (deterministic skills only, novel situations escalate to human). Phase 4 designs: which open-source models are supported, minimum GPU requirements for local inference, model update mechanism for air-gapped environments.
11. **Deployment model migration:** How does a customer migrate from fully on-prem to hybrid (or vice versa)? Data migration path, configuration change process, and downtime expectations need design before the second deployment model ships.
12. **Phase 1 credential model:** No Site Manager in Phase 1, but the full security model requires Site Manager for JIT credential fetching. Phase 1 likely needs local credential config (encrypted at rest) with migration to Site Manager credential proxy in Phase 2. Resolve before Phase 1 development starts. (CEO review finding)
13. **Cross-layer "wow demo" technical path:** The wow demo requires correlation between hardware faults and application-layer symptoms. The agent collects hardware telemetry (Redfish) and OS metrics but has no application-layer instrumentation. How does the agent know an application is slow? Options: scrape Prometheus, read application logs, receive application events via API. Resolve before day 30. (CEO review finding)
14. **Air-gapped agent discovery:** Use static IP configuration (--site-manager-ip flag) for air-gapped environments where DNS doesn't resolve. (CEO review decision: accepted)
15. **Vault unreachable fallback:** Agent caches credentials for 15-minute TTL after fetch. If vault is unreachable, cached credentials allow action execution within the window. After TTL expiry, escalate to human. (CEO review decision: accepted)
16. **LLM prompt injection via telemetry:** Sanitize all hardware telemetry data before including in LLM prompts. Strip non-printable characters, enforce max field lengths, tag telemetry as untrusted-origin. Human approval gate is defense-in-depth. (CEO review decision: accepted)
17. **Stale approval re-validation:** After approval is received, agent re-checks the skill condition before executing. If condition no longer matches (problem resolved), cancel the action with a 'condition cleared' notification. (CEO review decision: accepted)
